# 任务：实现通用 Claude Code 中文输出守卫（zh-reply-guard）

基于 Claude Code 官方 Hooks 机制，实现一个可独立使用、可公开发布的 `zh-reply-guard`。

目标不是简单添加"请使用中文"的提示词，而是：**用官方语言设置和提示注入做预防，用 Hook 校验实际输出做兜底**，在明确违规时要求 Claude 改用中文。

三个核心特点：**默认中文、尊重用户语言要求、零额外模型调用。**

---

## 〇、参考项目

主要参考 [minorun365/claude-code-japanese-guard](https://github.com/minorun365/claude-code-japanese-guard)（Apache-2.0，Python）。它是同一思路的日文版，已在实际使用中迭代过多轮，提交记录里能看到它踩过的坑。

**直接借鉴的做法**

| 做法 | 来源中的教训 |
|---|---|
| 同时用 `last_assistant_message` 和 transcript 判定最终回复 | Stop 触发时 transcript 可能还没写入最终回复；`last_assistant_message` 只有最后一条，回复被分成几段时前面的部分要从 transcript 里补 |
| 检查本轮的进度播报，但只看多行或很长的段落 | 一行的工具调用前置说明在界面上显示得很小；把它也拦下，会在中文最终回复之后多出一条只重写前置说明的消息，反而更难读 |
| 用 `mcp__.*__wrap_up` 匹配桌面端工具，在显示前拦截 | 只写 `wrap_up` 会被当成精确匹配，匹配不到带 `mcp__` 前缀的真实工具名 |
| 反馈里列出违规段落的首行，要求"只重写英文的部分，已经发出的中文不要再发" | 避免 Claude 把整段回复重复一遍 |
| 提供 `--check <transcript>` 命令，用过去的会话记录检查判定结果 | 方便用真实数据调阈值 |
| Markdown 链接整体剔除，并且在剔除 URL 之前处理 | 来源 issue #3：先剔 URL 会留下英文链接标题，导致误拦 |

**与参考项目的不同之处**

| 方面 | japanese-guard | zh-reply-guard |
|---|---|---|
| 目标语言 | 日文 | 简体中文 |
| 运行环境 | Python 3（Windows 上经常没装） | Node.js 18+，零依赖 |
| 用户要求其他语言 | 不处理 | 支持豁免（第五节） |
| 检查范围 | 最终回复、进度播报、wrap_up | 另外加上问题卡和任务列表 |
| 判定规则 | 英文字母数 > 日文字符数 × 3 | 识别英文句段，同时看词数和占比（第四节） |
| 安装方式 | 让 Claude 自己改 settings.json | 插件为主，另提供安装脚本 |

**许可**：用 Node.js 重新实现，不直接移植代码。README 的"致谢"一节写明设计参考了该项目。如果实现过程中移植了它的代码片段，项目就要遵守 Apache-2.0：保留原版权声明和 NOTICE 内容，并注明改动。

另外两个项目只借鉴一点：

- [Nanako0129/stingray](https://github.com/Nanako0129/stingray) 会读取 Claude Code 官方的 `language` 设置来确定目标语言，本项目也这样做（第五节）。它通过外部 API 判定语言，不符合本项目零模型调用的原则，这一点不采用。
- [thinceller/dotfiles PR #110](https://github.com/thinceller/dotfiles/pull/110) 用 339 条真实回复校准过阈值，本项目照这个方法校准默认阈值。

## 一、核心目标与覆盖范围

默认使用简体中文处理所有面向用户的自然语言内容，同时尊重用户明确要求使用其他语言的情况。

| 输出类型 | 机制 | 能力 |
|---|---|---|
| 最终回复 | `Stop`：读取 `last_assistant_message`，再从 transcript 补上本轮最后一次工具调用之后的文字 | 可拦截。英文已经显示给用户，拦截后 Claude 只补写英文部分的中文版本，原文无法撤回 |
| 进度播报（工具调用之间的文字） | `Stop`：从 transcript 读取本轮内容 | **只能事后补写**，无法在显示前拦截。只检查多行或很长的段落，一行的前置说明不检查 |
| 问题卡（`AskUserQuestion`）、任务列表（`TodoWrite` 等任务类工具） | `PreToolUse`：检查 `tool_input` 中的文案字段 | 显示前拦截：拒绝后 Claude 用中文重新调用 |
| 桌面端 wrap_up 的 recap 和按钮、update_plan 的任务列表 | `PreToolUse`：匹配 `mcp__.*__wrap_up`、`mcp__.*__update_plan` | 显示前拦截。参考项目已经在 wrap_up 上实际用过；CLI 用户没有这些工具，匹配不到也没有影响 |
| 子代理输出 | 不处理 | 子代理的输出交给主 Claude，不直接面向用户 |

不采用的机制（写进 README 的"能力边界"一节）：

- `MessageDisplay`：只改屏幕显示，Claude 看到的仍是原文，而且改写要靠翻译，违背零模型调用原则。
- `SubagentStop`：子代理输出不面向用户；新版本里子代理的报告通过 `SubagentHandback` 交付，`last_assistant_message` 里没有报告正文。

## 二、通用中文规则

以下规则用于两处：预防（`SessionStart` 注入，条件见 5.1），以及检测到违规时作为反馈原因的基础。

1. **语言规则**：默认使用简体中文输出所有面向用户的自然语言内容，包括最终回复、进度播报、任务列表、问题卡、总结和按钮文案。代码、命令、文件路径、API 名称、标识符、日志及提交信息按实际需要保留原文。

2. **发现英文内容时**：只把下面列出的英文段落改用简体中文重写，保持原意、事实和结构不变。已经用中文发出的内容不要再发一遍。进度播报只需写清关键进展。不要道歉，也不要解释为什么重写。之后的回复全部使用简体中文。

3. **例外规则**：如果英文内容本身就是用户要求的交付物，例如英文文案、README、PR 描述、提交信息、报错原文、引用内容或翻译结果，不要擅自翻译，只把周围的说明文字改为简体中文。

4. **语言优先级**：用户明确指定的输出语言高于默认中文规则。用户要求英文、日文或其他语言时，应尊重该要求。

5. **保持原始内容**：不得为了满足中文检测而修改代码逻辑、工具调用参数、文件内容、命令、测试结果或技术术语。

规则文本只使用"用户"等通用称呼，不得出现固定用户名、个人标识、特定机器路径或开发者专属配置。

## 三、Hook 架构

使用单个 Node.js 脚本 `hooks/zh-reply-guard.mjs`，按输入中的 `hook_event_name` 分派处理。零第三方依赖，Node.js 18+。

实现前必须重新查阅官方 Hooks 文档（https://code.claude.com/docs/en/hooks），核对下面用到的字段和协议，不得凭记忆使用过时接口。

### 3.1 事件与职责

| 事件 | 职责 | 输出 |
|---|---|---|
| `SessionStart` | 按 5.1 的条件注入第二节规则。matcher 为 `startup\|resume\|clear\|compact`，上下文压缩后重新注入 | `additionalContext`；不满足条件时不输出 |
| `UserPromptSubmit` | 识别用户的语言意图，写入会话状态（第五节） | 不输出 |
| `Stop` | 检查本轮的最终回复和进度播报（3.4） | 违规时阻断，否则静默放行 |
| `PreToolUse` | 检查配置中列出的工具的文案字段 | 违规时 `permissionDecision: "deny"`，否则静默放行 |

### 3.2 输出协议

- 放行：不向 stdout 写任何内容，退出码 0。
- `Stop` 阻断：stdout 输出 `{"decision":"block","reason":"<中文反馈>"}`，退出码 0。反馈中列出违规段落的首行（最多 5 段，每段截取前 80 个字符，进度播报标注"进度播报"），再附上第二节规则 2。
- `Stop` 的可选 `context` 模式：输出 `hookSpecificOutput.additionalContext`（`hookEventName: "Stop"`），效果同样是让 Claude 继续，但不显示 Hook 报错。默认用 `block` 以兼容旧版本；当前版本确认支持后，再在 README 中推荐 `context`。
- `PreToolUse` 拒绝：stdout 输出 `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<中文反馈>"}}`，退出码 0。**禁止使用 `updatedInput` 改写工具参数。**
- 只用 JSON + 退出码 0 这一种方式，不混用退出码 2。
- 任何异常（JSON 解析失败、字段缺失、内容为空、transcript 或状态文件读写失败）一律静默放行，退出码 0，错误只写入调试日志。

### 3.3 会话状态

- 存放位置：`os.tmpdir()/zh-reply-guard/<session_id>.json`，`session_id` 先做文件名安全处理。
- 内容：语言覆盖（语言、作用范围、来源 `prompt_id`）和本轮各工具的拒绝次数。
- 每次写入时顺带清理超过 7 天的状态文件。
- 只保存判定结果，不保存 prompt 原文或回复原文。

### 3.4 读取本轮内容（Stop）

transcript 的格式不是官方公开接口，只能尽力而为：读取失败或格式对不上时，只用 `last_assistant_message` 判定。README 要说明 Claude Code 升级后这部分可能失效。

1. **确定本轮范围**：取 transcript 中最后一条真实的用户输入之后的内容。带 `tool_result` 的条目和 `isMeta` 条目不算用户输入。
2. **区分最终回复和进度播报**：assistant 条目中，最后一个 `tool_use` 之后的 `text` 是最终回复，之前的 `text` 是进度播报。`thinkingDisplay` 为 `updates` 时，内容非空的 `thinking` 块也会显示为进度播报，同样检查。字段名以实现时的实际 transcript 为准，并用测试样本固定下来。
3. **处理写入滞后**：`last_assistant_message` 已经判为违规时立即阻断，不等待；否则如果 transcript 末尾还不是本轮的最终回复，每 100ms 重读一次，最多等 `waitSeconds`（默认 3 秒）。
4. **合并结果**：`last_assistant_message` 违规而 transcript 里没找到相同段落时，把它补进违规列表。
5. 只在内存中处理本轮内容，不保存也不上传。

## 四、语言检测策略

确定性规则，可解释、可配置。原则：**只判定"明显的大段英文自然语言"，无法确定时放行。**

### 4.1 预处理（剔除不参与判定的内容，按顺序执行）

1. Markdown 代码块（```` ``` ```` 与 `~~~`）、行内代码
2. Markdown 链接整体（包括链接文字），**必须在剔除 URL 之前处理**
3. URL、邮箱、HTML 标签
4. 引用块（`>` 开头的行），用于覆盖"英文引用"的场景
5. Windows / Unix 文件路径
6. 命令行（以 `$ `、`PS> ` 等提示符开头的行）
7. 标识符类词元：含 `_` `.` `/` `::` `-` 的词、驼峰词、全大写缩写、字母和数字混合的词

### 4.2 判定

1. 在剩余文本中找"英文句段"：连续不少于 `minSentenceWords` 个拉丁词，并且至少含 2 个英文常用虚词（the、is、are、to、of、and、that、this、will、you、we 等）。**用虚词区分英文句子和夹在中文里的技术名词。**
2. 统计英文句段总词数 `E` 和中文字符数 `C`（统计 CJK 统一汉字，含扩展 A 区），计算英文占比 `R = E / (E + C / 2)`，约 2 个汉字折算为 1 个英文词。
3. 同时满足 `E >= minEnglishWords` 和 `R >= minEnglishRatio` 才判为违规。

日文中的汉字会计入 `C`，所以日文回复会被放行。README 要写明这是有意为之：本工具只拦英文。

### 4.3 默认阈值（初始值，用第八节的真实样本校准后写进 README）

| 配置项 | 最终回复 | 进度播报（多行） | 进度播报（单行） | 工具文案 |
|---|---|---|---|---|
| `minSentenceWords` | 6 | 6 | 6 | 4 |
| `minEnglishWords` | 12（校准前为 30） | 12 | 50 | 8 |
| `minEnglishRatio` | 0.5 | 0.5 | 0.5 | 0.5 |

- 参考项目的进度播报阈值是多行至少 60 个英文字母、单行至少 250 个，按每词约 5 个字母折算成上表的初始值。
- 工具文案通常很短（按钮只有 1～3 个词），单独设阈值。同一次工具调用的所有文案字段合并后再判定，不逐字段判定。

### 4.4 工具文案字段

- 内置已知工具的字段白名单：`AskUserQuestion` 的问题、标题、选项标签和说明；`TodoWrite` 的任务内容；wrap_up 的 `recap`、`ask`、`actions[].label`（`actions` 可能是 JSON 字符串，需要先解析）；update_plan 的 `items[].content`。字段名以实现时的实际工具定义为准。
- 用户在配置中添加的工具：递归收集 `tool_input` 中的字符串值，跳过 `id`、`command`、`path`、`file_path`、`url`、`action` 等非文案字段。

## 五、目标语言与用户语言豁免

### 5.1 官方 `language` 设置

Claude Code 的 settings.json 有官方的 `language` 字段，会作为"始终用该语言回复"的指令传给 Claude。按 local → project → user 的优先级读取（`.claude/settings.local.json`、`.claude/settings.json`、用户目录下的 `settings.json`，用户目录要考虑 `CLAUDE_CONFIG_DIR`）：

- 值表示中文：照常检测，`SessionStart` 不再注入规则，避免重复。判断时去掉首尾空白、不区分大小写，`Chinese`、`chinese`、`中文`、`简体中文`、`简体`、`汉语`、`zh`、`zh-CN`、`zh_CN`、`zh-Hans`、`Simplified Chinese` 等都算中文。其他汉化工具会写入 `"language": "Chinese"`，这种写法必须识别为中文，否则守卫会被误停用。
- 未设置：照常检测，`SessionStart` 注入规则。README 建议用户设置 `"language": "简体中文"`，作为最基础的预防手段。
- 值表示其他语言：**整个守卫停用**，因为用户已经明确选择了别的语言。
- 读取或解析失败：按未设置处理。

### 5.2 对话中的语言意图

`Stop` 和 `PreToolUse` 的输入中没有用户 prompt，所以由 `UserPromptSubmit` 识别意图并写入会话状态。

先去掉 prompt 中的代码块和引用块（粘贴进来的英文不算用户的意图），再匹配：

- 指定语言：用 / 以 / 改用 / 切换到 + 英文 / 英语 / 日文 / 日语 / 其他语种 + 回复 / 回答 / 写 / 输出；`reply / answer / respond / write in English` 等。
- 翻译：翻译成 / 译为 + 语种；`translate ... into / to English`。
- 英文交付物：英文 README / 文档 / 文案、PR 描述、提交信息、`commit message`、`PR description`。
- 恢复中文：改回中文、恢复中文、用中文回答，清除覆盖。

### 5.3 作用范围

- 默认只在当前轮生效，以 `prompt_id` 标识。输入中没有 `prompt_id` 时，以下一次 `UserPromptSubmit` 为界。
- prompt 中含"以后 / 接下来 / 从现在起 / 全程 / from now on / always"时，整个会话都生效，直到用户要求恢复中文。

### 5.4 边界（写进 README）

- 关键词识别必然有漏判，漏判时用户可以手动临时禁用（第七节）。
- 用户用英文提问不算明确要求，默认仍回复中文。
- 宁可漏拦，不可误拦：识别到任何语言意图时，本轮完全放行，不再细分交付物和说明文字。

## 六、防止无限重试

- `Stop`：`stop_hook_active` 为 `true` 时直接放行，所以每轮最多阻断 1 次，即使 Claude 重写后仍是英文也放行。官方另有连续 8 次的上限兜底，但不依赖它。
- `PreToolUse`：官方没有对应的防循环字段，需要自己计数。同一轮内同一工具最多拒绝 1 次，之后放行。计数按 `prompt_id` 隔离，新一轮自动重置。
- 反馈要简短，只包含违规段落的首行和相关规则，减少上下文占用。

## 七、配置与安装

### 7.1 安装方式

1. **插件（首选）**：仓库本身是一个 Claude Code 插件，通过 `hooks/hooks.json` 声明 Hook，脚本路径用 `${CLAUDE_PLUGIN_ROOT}` 定位。安装时不修改用户的 `settings.json`，卸载也干净。README 提供添加 marketplace 和安装插件的命令。
2. **手动安装（备选）**：`node scripts/install.mjs`，支持 `--project` 和 `--uninstall`。
   - 全局安装：脚本复制到 `~/.claude/hooks/`，配置合并进 `~/.claude/settings.json`。
   - 项目安装：脚本复制到 `.claude/hooks/`，配置合并进 `.claude/settings.json`，路径使用 `${CLAUDE_PROJECT_DIR}`。
   - 合并前备份原文件；重复安装不产生重复条目；用固定标记识别自己的条目；卸载只删除自己的条目；不改动其他 Hook 和设置。
   - 原文件不是有效 JSON 时停止并提示，不覆盖。
3. **PreToolUse 的 matcher** 要写成正则：`AskUserQuestion|TodoWrite|mcp__.*__wrap_up|mcp__.*__update_plan`。只含字母、数字、`_` 和 `|` 的 matcher 会按精确匹配处理，匹配不到 MCP 工具。

### 7.2 跨平台

- 优先用 exec 形式：`"command": "node"`，`"args": ["<脚本路径>"]`，不经过 shell。`node.exe` 是真正的可执行文件，符合 Windows 下 exec 形式的要求。
- 命令里不写 `~` 或 `$HOME`：Windows 上没装 Git Bash 时，Hook 由 PowerShell 执行，不认这两种写法。
- 在 macOS、Linux、Windows（装与不装 Git Bash）上实测：`args` 里的 `${CLAUDE_PLUGIN_ROOT}` / `${CLAUDE_PROJECT_DIR}` 能否展开；路径含空格或中文时能否正常运行。不能展开就改用 shell 形式，并给路径加引号。
- stdin 和 transcript 都要兼容 UTF-8 BOM 和 CRLF。

### 7.3 可选配置

配置文件 `zh-reply-guard.json`，查找顺序：项目 `.claude/` → `~/.claude/` → 内置默认值。没有配置文件也能开箱即用。

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关 |
| `stopMode` | `"block"` | `block` 或 `context` |
| `checkProgress` | `true` | 是否检查进度播报 |
| `waitSeconds` | `3` | 等待 transcript 写入最终回复的上限 |
| `reply` / `progress` / `tool` | 见 4.3 | 各组阈值 |
| `tools` | `["AskUserQuestion", "TodoWrite", "mcp__.*__wrap_up", "mcp__.*__update_plan"]` | 要检查的工具，支持正则 |
| `injectRules` | `true` | 是否允许 `SessionStart` 注入规则（仍受 5.1 的条件限制） |

环境变量优先级高于配置文件，可以写在 settings 的 `env` 字段中：

- `ZH_REPLY_GUARD=off`：临时禁用全部检测
- `ZH_REPLY_GUARD_DEBUG=1`：开启调试日志

调试日志写入 `os.tmpdir()/zh-reply-guard/debug.log`（JSONL 格式），只记录事件、判定结果和统计数值（`E`、`C`、`R`），**不记录回复或 prompt 原文**。

### 7.4 命令行检查工具

`node hooks/zh-reply-guard.mjs --check <transcript.jsonl>`：对指定会话记录的最后一轮运行同样的判定，打印违规段落的首行和统计数值，不阻断任何操作。用于排查误判和校准阈值。

## 八、测试与校准

使用 `node --test`，零依赖。测试分两层：纯函数单测（预处理、检测、意图识别、transcript 解析），以及以子进程方式向脚本传入 Hook JSON、断言 stdout 和退出码的端到端测试。

| 场景 | 预期 |
|---|---|
| 完整中文回复 | 放行，stdout 为空 |
| 大段英文解释 | 阻断，`reason` 为中文并列出违规段落首行 |
| 中文夹杂技术英文（如 React、API、token） | 放行 |
| 中文解释 + 英文代码块 | 放行 |
| 中文解释 + 英文命令、路径、URL、API 名称 | 放行 |
| 中文 + 英文标题的 Markdown 链接 | 放行 |
| 中文技术文章 + 英文引用块 | 放行 |
| 很短的英文回复（低于阈值） | 放行 |
| 阈值边界：略低于 / 略高于阈值 | 分别放行 / 阻断 |
| 日文回复 | 放行 |
| 中文最终回复 + 多行英文进度播报 | 阻断，只列出进度播报 |
| 中文最终回复 + 一行英文前置说明 | 放行 |
| `thinkingDisplay: updates` 下的英文 thinking 播报 | 按进度播报判定 |
| transcript 尚未写入最终回复，`last_assistant_message` 为英文 | 立即阻断，不等待 |
| transcript 尚未写入，`last_assistant_message` 为中文 | 最多等待 `waitSeconds` 后判定 |
| transcript 不存在或格式异常 | 只用 `last_assistant_message` 判定 |
| prompt 要求英文回复 | 本轮放行，下一轮恢复检测 |
| prompt 要求"以后都用英文" | 整个会话放行，"改回中文"后恢复 |
| prompt 要求英文 README / 翻译成英文 / 英文 PR 描述 / 提交信息 | 本轮放行 |
| prompt 中粘贴的英文代码含 "English" | 不视为语言意图 |
| `language` 设为中文 / 未设置 / 设为英文 | 检测且不注入 / 检测并注入 / 整体停用 |
| `language` 为 `"Chinese"`、`"zh-CN"`、`" 简体中文 "` 等写法 | 都识别为中文 |
| `SessionStart` 的 `source` 为 `compact` | 重新注入规则 |
| `stop_hook_active: true` + 英文 | 放行 |
| `AskUserQuestion` 英文问题和选项 | 拒绝，反馈为中文 |
| wrap_up 的 `actions` 是 JSON 字符串且为英文 | 解析后拒绝 |
| 同一轮内同一工具第二次英文调用 | 放行（防循环） |
| 新一轮的同一工具英文调用 | 再次拒绝 |
| 未列入 `tools` 的工具 | 不检查 |
| 空回复、非法 JSON、字段缺失、stdin 带 BOM | 静默放行，退出码 0 |
| 状态目录不可写 | 静默放行 |
| `ZH_REPLY_GUARD=off` | 全部放行 |
| `install.mjs`：已有其他 Hook、重复安装、卸载、原文件 JSON 无效 | 不破坏已有配置 |

**校准**：参照 thinceller 的做法，用 `--check` 在本机真实会话记录上批量运行，统计误拦和漏拦，据此确定 4.3 的默认值。真实记录只在本机使用，不提交到仓库；`tests/fixtures/` 里只放脱敏后的片段。

测试样本要覆盖多种写法，不得为固定样例硬编码判断；调整阈值后必须跑完整的样本集。无法靠 Hook 输入可靠识别的场景（例如没有关键词的隐含语言意图），只测试其边界，并在 README 里说明用户如何手动豁免。

## 九、README 要求

用简体中文编写，面向普通 Claude Code 用户，包含：

- 项目作用和适用场景
- 为什么只写 `CLAUDE.md` 或设置 `language` 有时还不够：长时间的工具调用之后、读过英文工具输出之后，回复容易切换成英文
- 工作原理：官方设置和规则注入负责预防，Hook 校验负责兜底，并说明各事件分别负责什么
- 安装与卸载（插件 / 手动 / 项目级），命令可以直接复制执行
- 完整配置示例
- 默认规则与例外规则
- 语言检测算法、阈值含义、误判处理（`--check`、调试日志、调整阈值、临时禁用）
- **能力边界**：进度播报只能事后补写；`Stop` 拦截后原英文仍然可见；transcript 格式不是官方接口，可能随版本失效；语言意图识别依赖关键词；只拦英文
- 常见问题和故障排查（Hook 没有触发、matcher 写成精确匹配、Windows 路径、Node 不在 PATH 中、与其他 Hook 共存、与其他汉化工具共存）
- 致谢：设计参考了 claude-code-japanese-guard

## 十、工程质量

- 实现轻量、清晰，不引入框架和不必要的抽象。
- 只用确定性规则，不调用任何模型或网络服务。
- 只读取 Hook 输入、当前会话 transcript 的本轮内容和 settings 中的 `language` 字段，不保存、不上传任何内容。
- 正常情况下不向 stdout 和 stderr 输出任何内容。
- 所有阻断反馈符合官方协议。
- 如果已有相关实现，优先复用和改进。
